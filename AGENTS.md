# AGENTS.md

Restaurant POS web app ("TableManager 2.1C") served directly by Apache from this directory. Romanian-language UI.

## Stack & runtime
- Plain PHP + vanilla JS + CSS. No framework, no build step, no package manager, no tests/lint/typecheck, not a git repo.
- Deploy = edit files and refresh the browser. There is nothing to "run" or "build".
- Backend talks to **MSSQL** via the `sqlsrv` PHP extension (server must have `php_sqlsrv` loaded).
- **Printing** is handled by a separate Python service in `print-service/` (Windows Python 3.12), which polls a durable queue in MSSQL through `api/print_queue.php` and delivers ESC/POS. Start it with `print-service/start-print-service.bat` (add a shortcut to `shell:startup` for autostart). It listens only on `127.0.0.1:8756`. See "Tiparire" below.

## Tiparire (print-service + coada durabila)
- The whole printing flow is asynchronous and durable: business actions only write a job row into `tblPrintQueue` (in the same transaction as the action), and the Python service picks it up, renders it and delivers it. If the printer is off, the job stays `pending` and is retried with backoff until the printer comes back — nothing is lost.
- `tblPrintQueue` (auto-created by `ensurePrintQueueTable()` in `api/print_common.php` if missing): `JobID` IDENTITY PK, `Tip` (`kitchen`|`nota`|`proforma`|`fiscal`|`raport`), `RefDocID`, `PrinterNr` (`tblKP.NrLogic`, kitchen only), `Payload` (JSON), `Stare` (`pending`|`printing`|`done`|`failed`), `Attempts`, `NextAttempt`, `LastError`, `CreatedAt`, `PrintedAt`.
- `api/print_queue.php` is the only component that touches the queue table; the Python worker has **no DB driver** and talks to it over HTTP:
  - `GET ?action=claim` — atomic claim (`WITH (UPDLOCK, READPAST)` + `UPDATE ... OUTPUT`), marks the job `printing`, `Attempts++`, returns the payload.
  - `POST {action:'done'|'fail', jobId, error?, retryInSeconds?, permanent?}` — the worker reports the result; `fail` reschedules (`NextAttempt = GETDATE()+retry`) or marks `failed` when permanent.
  - `GET ?action=list|status` + `POST {action:'retry'|'delete'|'clear_done'}` — for the POS "Coada printare" screen.
- `print-service/` (Python): `server.py` (HTTP `/health`, `/wake`, `/preview/<file>`), `worker.py` (claim → build → deliver → report loop), `escpos.py` (ESC/POS builder: align/bold/underline/size (`GS ! n`)/font (`ESC M`)/cut + diacritic transliteration), `emulator.py` (decodes the ESC/POS subset to HTML = the emulator used until the physical printer arrives), `targets.py` (`preview`/`file`/`windows` raw via pywin32/`network` socket :9100), `config.json`/`config.py`. `api_base` is `https://127.0.0.1/rual/api` with `verify_ssl:false` (the site forces HTTPS). Retry policy in `config.json`: `backoff_seconds` `[5,15,30,60,300]`, `max_attempts` 50.
- Kitchen tickets are grouped by `tblProd.KP` → `tblKP.NrLogic` (config `printers` maps each `NrLogic` to a target); modifier rows are attached to the preceding product; storno rows print as `ANULARE`. Each printer gets one job.
- The **emulator** renders every `kitchen`/`nota` job to `print-service/preview/job_<JobID>.html` (also timestamped + `ultimul.html`); the POS shows it in `#modal-print-preview`. The `fiscal` job writes the Datecs/FiscalNet text to `print-service/spool/fiscal/`.
- To switch to the real printer, change the target in `config.json` to `{"target":"windows","name":"<printer name>"}` (needs `pip install pywin32`) or `{"target":"network","host":"...","port":9100}`. Windows targets first check `PRINTER_STATUS_OFFLINE/ERROR` so an offline printer is retried instead of silently held by the spooler.

## Database
- Connection is in `api/db.php` (`getDBConnection()`); DB `Rual`, `CharacterSet => UTF-8`, `ReturnDatesAsStrings => true` (dates/`GETDATE()` come back as strings). Server/user/password come from `api/db.local.php` (git-ignored, holds the real credentials); `db.php` falls back to placeholder values when that file is missing. Use `api/db.local.example.php` as a template.
- Store ID `MagID = 11` is hardcoded across queries. Default cashier is `nrOp = 8`.
- Queries use positional `?` params with `sqlsrv_query($conn, $sql, [$params])` — no named params.
- `ECRID` (`tblNoteD`) and `DocID` (`tblBonCurent`) are `IDENTITY` columns: omit them on INSERT, read new ID via `SCOPE_IDENTITY()`.

## Key schema (Rual DB)
- `tblGrp` — menu groups (positioned by `Poz`, styled by `BackColor`/`FontColor`/`Bold`). `menu.php` also returns and applies `FontSize` (px) and `FontType` (font-family); group buttons in the menu grid and the `#screen-prog-grupe` live grid both honour them.
- `tblProd` — products; price is `tblProd.PV`. The obsolete `tblPV` table is no longer referenced anywhere (safe to `DROP TABLE tblPV`); all price reads use `COALESCE(tblProd.PV, 0)`. The legacy `tblProd.TVA` column is dropped; the VAT rate for a sale line is resolved via `tblProd.Nr_TVA -> tblTVA.Cota` and stored on the line as `tblNoteD.TVAc`. `tblProd.MZ` (int 0/1) marks whether the product is part of the "Meniul Zilei" and is edited as a Da/Nu toggle in the Produse programming screen.
- `tblSectii` — sections (`Sectie` INT PK, `Denumire` NVARCHAR(10)); referenced by `tblProd.Sectie` and shown as a combo in the product editor. Edited via `api/sectii.php` (GET list + POST insert/update/delete); `Status` column is never shown/used. Sections `1` and `2` are protected and cannot be deleted (server rejects them; the UI disables the Sterge button).
- `tblBonCurent` — bills; `Stare = 'D'` = open, `'I'` = closed. `tblNoteD` — bill line items. The legacy `tblNoteD.Val` column is dropped: a line's value is always computed as `Cant * PV`. `tblNoteD.PV` is the current line price (changed by discount); `tblNoteD.PVC` is the catalog price at insert time, kept to allow undoing a discount. `tblNoteD.[Comment]` NVARCHAR(50) stores the discount motive on the discounted lines (NULL otherwise). `tblNoteD.StornoRef` INT NULL links a void/storno line to the original line's `ECRID`. `TotalB` is recalculated as `SUM(Cant * PV)`.
- `tblMese` — table config; `tblOsp` — waiters (auth by `Parola`, `Blocat = 0`).
- `tblMesaj` — prep-mode ("mod preparare") texts, keyed `NrMesaj` + `Mesaj` (alphabetical list).
- `tblParola` — single-row POS passwords (`Id = 1`, nvarchar(20)): `ParolaProgramare`, `ParolaRapoarte`, `ParolaStornare`, `ParolaDiscount`, `ParolaExit`. Empty string/NULL = password not required. `authenticate` checks `ParolaProgramare` first and returns `programare: true` to open the programming screen, then `ParolaRapoarte` returning `rapoarte: true` to open the reports screen; otherwise falls back to `tblOsp`. `void_line` checks `ParolaStornare` for sent lines.
- Colors are Windows `COLORREF` (0x00BBGGRR); converted to hex in `api/menu.php`.
- `tblNrZ` — Z closure register: `NrZ` (int, last Z number; next = `ISNULL(MAX(NrZ),0)+1`), `NRNota` (last `NrDoc` archived), `Data`, `Ora`, `Id` (IDENTITY PK). `tblBon` — archive of `tblBonCurent`: `DocID` is the PK (not IDENTITY, preserved from source) plus `s_Generation`/`s_GUID`/`s_Lineage`/`DocIDP`, and it lacks `Preluat`/`BonTableta`/`StatusBonTableta`/`StatieID`/`OrderID`. `tempECR` — archive of `tblNoteD` (legacy layout with `Val`, `Cont`, `Procent`, `ValPr`, `PretRaft`, `Denumire`); **`ECRID` is IDENTITY in `tempECR`** so it must be omitted on insert; `Val` is written as `Cant*PV`, `PretRaft` as `PVC`, `Denumire` as the product name/descriere (`LEFT(...,32)`), `Cont`/`Procent`/`ValPr` NULL. `trelArhZDocIDFpID` — archive of the day's `trelDocIDFpID` payments (`Id` IDENTITY PK, `DocID`, `FPID`, `FPDenumire` nvarchar(10), `Suma`).

## "Mod preparare" (modifiers) storage convention
- A modifier is its own `tblNoteD` row: `ProdID = 0`, `Cant = 0`, `PV = 0`, `PVC = 0`, `NrGrp = tblMesaj.NrMesaj`, `Descriere` = message text. It never affects `TotalB`.
- `get_order.php` orders lines by `OraComanda, ECRID` (so the note shows newest additions last, not pure global `ECRID`), detects modifier rows by `Cant <= 0` and nests them under the **preceding product line** as `articole[i].mods[]` (no FK to the product — grouping is positional). Client renders them indented under that product with a per-mod delete (`✕`). Only rows with `Cant <= 0` can be deleted via `delete_mod`, so product rows are safe.
- `transfer_products` reassigns moved lines to the destination `DocID` **and stamps them `OraComanda = GETDATE()`**, so a transferred product appears at the end of the destination note (the note is sorted by `OraComanda`).
- `add_product` always inserts a **new** `tblNoteD` row per tap — it never merges/updates an existing line of the same product. Change a line's quantity via the `update_qty` popup (keypad, single decimal allowed).

## "VD" (void/storno) storage convention
- A void line is a **real product row** with `Cant` negative and `PV` positive (value `Cant*PV` negative, so `TotalB` drops automatically). It is distinguished from a modifier by `ProdID > 0` (modifiers are `ProdID = 0 && Cant <= 0`). `StornoRef` = the original line's `ECRID`; `[Comment]` = void reason; `Preluat = 0` at insert.
- A storno row with `Preluat = 0` has not been sent to kitchen/bar yet, so it can be **revoked** by voiding it (`void_line` on a `Cant < 0` row deletes it and restores the original line's discount proportionally). `Marcare` (`print_kitchen`) sets `Preluat = 1` on the rows that are still `Preluat = 0` (stornos included); after that a storno can no longer be revoked.
- A storno line is always written at the **catalog price** (`PV = PVC`), never at the discounted `PV`. When a sent line that carries a discount is voided, the line's discount is rescaled proportionally to the remaining net quantity (`discAfter = discBefore * netAfter / netBefore`), so a valoric discount shrinks as quantities are voided and the total can never go negative. Because the discount is stored as `PV = PVC - disc/Cant` on the original line and stornos subtract the full `PVC`, the note stays consistent: `TotalB = (activeQty * PVC) - discount`.
- `Preluat = 1` means the line was already sent to kitchen/bar; `Preluat = 0` means it was not.
- Voiding an **unsent** line (`Preluat = 0`) deletes it (or decrements `Cant` on partial void); on full delete its positional modifier rows (`ProdID = 0 && Cant <= 0` following it) are deleted too. In the UI, unsent lines (and storno rows with `Preluat = 0`) are removed **directly, without a popup**; the VD popup only opens for sent product lines (quantity + reason + manager password). Voiding a **sent** line (`Preluat = 1`) never deletes the original: it inserts the negative storno row and requires the storno password (`tblParola.ParolaStornare`) + a reason.
- Cumulative voiding is capped: `SUM(-Cant)` over storno rows with the same `StornoRef` can never exceed the original line's `Cant`. `get_order.php` returns per-line `stornat`/`ramas`.
- The `Marcare` button is implemented (`print_kitchen`): it groups the unsent rows by `tblProd.KP`, enqueues one `kitchen` job per printer and sets `Preluat = 1` on those rows in the same transaction; the Python service then prints them.

## Autentificare ospatari (casieri)
- Un ospatar trebuie sa fie autentificat ca sa intre/deschida o masa sau sa marcheze produse, si nu poate intra pe o masa deschisa de alt ospatar. Autentificarea se face cu parola din `tblOsp` (`Parola`, `Blocat = 0`), prin modalul virtual (`#modal-keyboard`, `openLoginModal(cb)` -> `vkeyValidate()` cu `keyboardAction = "login"`), care accepta **doar** parola de ospatar (ignora raspunsurile `programare`/`rapoarte`).
- `tblSet.Setting = 'Mod_logare'` (`menu.php` il intoarce ca `modLogare`): `1` = ospatarul ramane logat toata sesiunea (persistat in `sessionStorage` sub `rual_waiter`, restaurat de `restoreWaiterSession()` la init); `0` = delogare automata la iesirea de pe masa (`navigateToScreen` apeleaza `logoutWaiter()` la trecerea marcare/plata -> mese).
- `POS_STATE` tine `loggedIn`, `nrOp`, `casierCurent`, `waiterRol`, `bonNrOp` (ospatarul care a deschis bonul curent) si `modLogare`. `setAuthenticatedWaiter()`/`logoutWaiter()` actualizeaza si eticheta `#current-cashier-label`.
- `selectTableAndOpen()` cere login (altfel `openLoginModal`), verifica proprietarul din `POS_STATE.tables[].nrOp` si dupa `loadOrder()` din `data.nrOp`; `addProduct()` cere login. Server-side, `add_product` si `transfer_products` refuza (403) daca bonul (sursa/destinatie) are `NrOp` diferit de `nrOp`-ul cererii. `get_order.php` si `get_tables.php` intorc `nrOp` (proprietarul bonului).

## API endpoints (all under `api/`)
- `menu.php` (GET) — groups + products with prices + `messages` (tblMesaj) + the `meniulZilei` setting + `distrRand1`/`distrRand2` (tblSet, used in the tables-screen footer). Each product also carries `MZ` (0/1). Real menu source.
- `get_order.php` (GET `?masa=N`) — open bill + items for a table; each item has nested `mods[]`, plus `pvc`, `valoareOriginala` (Cant*PVC, pre-discount) and `comment`. Response carries `subtotal` (catalog/gross), `total` (net, after discount) and `reducere`. Storno rows are returned as separate items with `storno: true` (negative `cantitate`/`valoare`) and their own `preluat`; normal items carry `preluat`, `stornat` and `ramas`.
- `get_tables.php` (GET) — status of 80 tables.
- `order_action.php` (POST JSON) — dispatcher on `action`: `add_product`, `toggle_cook`, `add_mod`, `delete_mod`, `update_qty`, `transfer_products`, `close_bill`, `print_kitchen`, `print_proforma`, `apply_discount`, `void_line`, `mark_sent`, `authenticate`.
- `print_kitchen` (POST `{docId}`) — the `Marcare` button (and the NOTA button). It reads the bill's not-yet-sent rows (`WHERE DocID = ? AND Preluat = 0`) via `printKitchen($conn, $docId)`, groups them by `tblProd.KP` (modifier rows attach to the preceding product), enqueues one `kitchen` job per printer in `tblPrintQueue` and sets `Preluat = 1` on those rows — all in one transaction, then wakes the Python service (`wakePrintService()`). The response carries `jobs`/`marcate`. Leaving a table via the marcare **Inapoi** (`handleInapoiBtn` -> `leaveTableToTables()`) also calls `print_kitchen` first, so unsent items are sent to the section printers when the waiter exits the table.
- `print_proforma` (POST `{docId}`) — the **Nota Proforma** button on the payment screen (`actionProforma()`). Builds the same non-fiscal note payload as `close_bill` via `buildBillPrintData($conn, $docId, $bon, [], "NOTA PROFORMA")` (no payments, bill stays open) and enqueues a single `proforma` job (Tip `proforma`, rendered by the worker exactly like `nota`, only the title differs).
- `close_bill` (POST `{docId, plati}`) — the `Nota` button / payment screen. `plati` is an associative array `FPID => amount` (e.g. `{"0":100,"1":200}` = 100 numerar + 200 card), supporting split payment. Delegates to `closeBill($conn, $docId, $plati)`: if the bill has no lines it is **deleted** from `tblBonCurent`, otherwise `Stare = 'I'` (+ `Ora = GETDATE()`) and one row per payment (`DocID`, `FPID`, `Suma`) is written to `trelDocIDFpID` (existing rows for the DocID are replaced), and in the same transaction `enqueueBillPrintJobs()` writes a `nota` (non-fiscal receipt; its header is strictly the `H1`-`H3` rows of `tblAntet`, footer `F1`-`F2`, plus lines + payments; each H/F row is printed with its own `NumeFont` (`ESC M`), `Size` (`GS ! n`) and `Bold` (`ESC E`), carried in the payload as `{text,font,size,bold}`) and a `fiscal` (Datecs/FiscalNet text) job into `tblPrintQueue` — all inside a single transaction. `TipDoc` (nvarchar(3)) is deliberately not written (doesn't fit the payment name). On the `Nota` button, a bill with total 0 is closed directly from `actionNota()` without opening the payment screen.
- `mark_sent` (POST `{nrMasa}`) — legacy action kept in the API; sets `Preluat = 1` on **all** rows of the open bill (products, modifiers and storno rows). No longer used by the UI (the `Marcare` button uses `print_kitchen`).
- `void_line` (POST `{ecrId, cantitate, motiv?, parola?}`) — voids the selected line: if it is a **storno** row (`Cant < 0`) with `Preluat = 0` it is deleted (revoking the void, restoring the original line's discount); if it is a product line with `Preluat = 0` it is deleted (or `Cant` decremented); if `Preluat = 1` it inserts a negative storno row (`Cant = -cantitate`, `PV = PVC`, `StornoRef = ecrId`, `[Comment] = motiv`, `Preluat = 0`) after checking `tblParola.ParolaStornare`. Rejects over-voiding (`cantitate > Cant - alreadyStornoed`). A storno row is written with `Preluat = 0`; it is printed to the kitchen as `ANULARE` by the next `Marcare`/`print_kitchen`.
- `apply_discount` (POST `{scope:'line'|'bill', mode:'percent'|'valoric', value, motiv?, ecrId?}`) — persists the discount in `tblNoteD` by rewriting `PV` (base is always the catalog price `PVC`). There is a **single active discount per bill**: it first resets all product lines `PV = COALESCE(PVC, PV)` and clears `[Comment]`, then applies the new one. A `line` discount targets one `ECRID`; a `bill` discount is distributed proportionally across lines grouped by VAT rate (`TVAc`), then within each group, using cents + largest-remainder so the sum is exact. The weights are the **net** values (`(Cant - alreadyStornoed) * PVC`, from `StornoRef`), so voided quantities don't skew the per-VAT-rate split; the discount is still subtracted from the line's gross value while the storno row keeps subtracting the full price. `[Comment]` is set to the motive on discounted lines. `TotalB` is recalculated.
- Product rows always keep `Cant > 0` (`update_qty` rejects 0, and rows with `Cant <= 0` are treated as modifiers) — a 0 qty would silently become a mod line.
- `update_qty` refuses to change a line already sent to the kitchen/bar (`Preluat = 1`); the client shows the qty cell locked (`.qty-locked`) and blocks the qty popup.
- `fiscal.php` — legacy fiscal preview endpoint (kept for reference); the real fiscal text is now built by `buildFiscalText()` (in `order_action.php`) and written by the Python service into `print-service/spool/fiscal/`.
- `print_queue.php` (GET `?action=claim|list|status|get` + POST `{action:'done'|'fail'|'retry'|'delete'|'clear_done'}`) — the durable print queue API used by the Python worker (claim/done/fail) and by the POS queue screen. `print_common.php` holds the shared helpers `ensurePrintQueueTable()`, `enqueuePrintJob()`, `wakePrintService()`. `print_preview.php?jobId=N` proxies the emulator HTML same-origin (avoids mixed content on the HTTPS POS).
- `rapoarte.php` (GET `?tab=X|Z&tip=PLU|Grupe|Sectii|Casieri|General` + POST `{action:'print', tab, tip}`) — report data and report printing. **X - PLU**, **X - Grupe**, **X - Sectii**, **X - Casieri** and **X - General** are implemented. `buildPluReport()` runs the PLU query (inner join `tblProd`/`tblSectii`, `ROUND(SUM(Cant),2)` and `ROUND(SUM(Cant*PV),2)`, grouped by section+product), returns `sectii[]` with `subtotalCant`/`subtotalValoare` per section plus a grand total. `buildGrupeReport()` aggregates `tblNoteD` by product group (`tblGrp`, alphabetical by `Denumire`, no product detail), returning `grupe[]` with just `valoare` per group. `buildSectiiReport()` is identical but groups by `tblSectii`, returning `sectii[]` with just `valoare` per section. `buildCasieriReport()` groups by `tblBonCurent.NrOp` (`tblOsp.Nume`), returning `casieri[]` with `nrBonuri` (`COUNT(DISTINCT DocID)`), `reducere` (`SUM(Cant*(PVC-PV))` on positive lines), `stornari` (`SUM(-Cant*PV)` on negative lines) and `total` (`SUM(Cant*PV)`, so the grand total matches PLU/Grupe) plus `plati[]` (payments from `trelDocIDFpID` joined to `tblFP`, only for the current-session DocIDs), and grand totals (`totalBonuri`/`totalReducere`/`totalStornari`/`totalPlati`/`totalValoare`). `buildGeneralReport()` returns the global totals (`totalBonuri`, `totalDiscount`, `totalStornari`, `totalValoare`), `plati[]` (total per payment form), `tva[]` (`cota`, `total`, `baza`, `suma` — PV is VAT-inclusive, base = total/(1+cota/100)) and `note[]` (`nrNota`=`tblBonCurent.NrDoc`, `nrMasa`, `ospatar`=`tblOsp.Nume`, `total`). `buildGroupedReportLines()` formats the text for PLU (`buildPluReportLines()`), `buildSimpleReportLines()` the group/section-only lists (`buildGrupeReportLines()`/`buildSectiiReportLines()`, value only), `buildCasieriReportLines()` the cashier blocks and `buildGeneralReportLines()` the general report; the POST enqueues a `raport` job carrying `headerLines` (the `H1`-`H2` rows of `tblAntet`, each with its `NumeFont`/`Size`/`Bold` — all report types from now on print this antet) + the text lines, rendered by the worker (`build_raport()` prints `headerLines` first, then the title, exactly like `build_nota()`; a report line may be a plain string or `{text,bold,size,font}`, and the final `TOTAL` line of every report is bold). **All X reports cover only closed bills** (`INNER JOIN tblBonCurent b ON d.DocID = b.DocID` + `WHERE b.Stare = 'I'`) and the current session (`tblNoteD` is emptied by the Z report).
- **Z closure** (`POST {action:'z', tipuri:[...]}`, plus `GET ?tab=Z&check=1` -> `{allowed, message, nextZ}`): `buildZReportLines()` builds the Z report (General Z, then a bold `RAPORT Z - <TIP>` section for each checked PLU/Grupe/Sectii/Casieri) **before** the clear, then calls the stored procedure `dbo.RealizeazaZ` which does the archiving + clearing atomically. The procedure (defined in `api/sql/z_procedure.sql`, auto-created by `ensureZProcedure()` on demand via `CREATE OR ALTER`) refuses to run unless **all tables are closed** (`tblBonCurent.Stare <> 'I'` -> `RAISERROR`), computes `@NrZ = ISNULL(MAX(tblNrZ.NrZ),0)+1`, writes the `tblNrZ` row (`NRNota` = last `NrDoc`), copies `tblBonCurent` -> `tblBon` (stamping `NrZ = @NrZ`), copies `tblNoteD` -> `tempECR` (omitting the IDENTITY `ECRID`), archives the day's payments from `trelDocIDFpID` into `trelArhZDocIDFpID` (`DocID`, `FPID`, `FPDenumire`=`LEFT(tblFP.Denumire,10)`, `Suma`) then deletes them (FK to `tblBonCurent`), deletes both source tables, all inside one `TRY/CATCH` + `XACT_ABORT ON` transaction (any error -> `ROLLBACK` + `THROW`, so nothing is done partially). The print job (title `RAPORT Z - GENERAL`, headerLines H1-H2) is enqueued after the successful commit.
- `tva.php` (GET list + POST `insert`/`update`/`delete`) — edit `tblTVA` (columns `Nr_TVA`, `Cota`).
- `mesaje.php` (GET list + POST `insert`/`update`/`delete`) — edit `tblMesaj` (columns `NrMesaj`, `Mesaj`); saves also refresh `POS_STATE.messages`.
- `ospatari.php` (GET list + POST `insert`/`update`/`delete`) — edit `tblOsp` (columns `NrOsp` text PK, `Nume`, `Expl`, `Parola`, `Blocat` bit).
- `kp.php` (GET list + POST `insert`/`update`/`delete`) — edit `tblKP` (columns `NrLogic` PK, `Serie`, `Stare`, `Nume`, `MagID`, `CaleTSC`, `raport`, `DenumirePrinter`).
- `mese.php` (GET list + POST `insert`/`update`/`delete`) — edit `tblMese`. `MasaID` is the IDENTITY PK used for update/delete; `NrMasa` (1..80) is the logical map position and is treated as unique (insert rejects a duplicate `NrMasa`). `BackColor`/`ForeColor` are COLORREF ints (also returned as hex); empty string = `NULL`. Drives the live 10x8 editor map and the real tables screen. On the real `screen-mese` a position is **not rendered at all** unless it has a row in `tblMese` with `Afisez = 1` or it has an open bill (which is always shown, even if `Afisez = 0`). `screen-mese` reloads `get_tables` on entry.
- `grupe.php` (GET list + POST `insert`/`update`, no delete) — edit `tblGrp`. `NrGrp` is the PK (no identity; entered manually on insert, read-only on update). Editable UI fields are `Denumire`, `Poz` (1..50), `BackColor`, `FontColor`, `FontSize`, `FontType`, `Bold`; `Tint`/`NrKp` are never shown (`UPDATE` leaves them untouched, `INSERT` sets `Tint = 0`, `NrKp = NULL`). Colors COLORREF ints + hex.
- `produse.php` (GET products + lists + POST `insert`/`update`/`delete`) — edit `tblProd`. `GET` accepts `?nrgrp=` to filter by group and returns `sectii` (from `tblSectii`: `Sectie`, `Denumire`) and `tva` (from `tblTVA`: `Nr_TVA`, `Cota`) for the inspector's combo boxes. `ProdID` is the PK (no identity; entered manually on insert, read-only on update). The editor edits all `tblProd` columns except `DataUM` (never shown; `DataUM` is always set to `GETDATE()` on both `insert` and `update`). The legacy `tblProd.TVA` column has been dropped from the schema. Colors COLORREF ints + hex.
 - `antet.php` (GET + POST `update`) — edit only the `tblAntet` row with `Seria = '0001'`. Columns: `Nume`, `Denumire2`, `Adresa`, `CodFiscF`, `RegCom`, `Judet`, `Cont`, `Banca`, `Oras`, `CodPostal`, `PersContact`, `email`, `website`, `telefon`, `PlatitorTVA` (int 0/1), `CaleDateLogo`, `QRCodeText`, `SizeModeLogo` (int).
 - `nota.php` (GET + POST `update`) — edit the `tblAntet` header/footer rows `Seria IN ('H1','H2','H3','F1','F2')`. Editable columns: `Nume`, `NumeFont`, `Size` (int), `Bold` (bit). `NumeFont` is the ESC/POS font token (`A`..`E`, chosen from a combobox) rather than a Windows font name; any legacy/unknown value is shown as Font A. `Size` stores the ESC/POS `GS ! n` parameter (bits 0-2 = height-1, bits 4-6 = width-1; e.g. `0`=1x1, `16`=2x1, `1`=1x2, `17`=2x2, `34`=3x3), chosen from a magnitude combobox (`NOTA_SIZES`); legacy point sizes are shown as 1x1. GET returns all five rows in fixed order (H1,H2,H3,F1,F2); POST `{action:'update', rows:[...]}` updates them in a single transaction.
 - `conectare.php` (GET + POST `update`/`test`) — edit the single `tblConectare` row (`ID = 1`, identity). Columns: `ServerIP`, `ServerName`, `DataBaseName`, `UserName`, `Password` (each nvarchar(50)), `TC` (bit, combobox Da/Nu) and `ODBC_connect_string` (nvarchar(255)). Read by `sync_products.php` (source connection). POST `{action:'test', ...}` tries `sqlsrv_connect` with the on-screen values (same server/instance merge as `sync_products.php`; `TC=1` means Windows auth, so UID/PWD are omitted) and reports success/failure.
 - `parole.php` (GET + POST `update`) — edit the single `tblParola` row (`Id = 1`). Columns: `ParolaProgramare`, `ParolaRapoarte`, `ParolaStornare`, `ParolaDiscount`, `ParolaExit` (each nvarchar(20), numeric-only; empty = password not required).
 - `fp.php` (GET list + POST `insert`/`update`/`delete`) — edit `tblFP` (columns `FPID` PK, `Denumire`, `Status`, `Poz`). `Poz` sets the display order of the payment buttons on the payment screen; GET returns rows ordered by `Poz` and the form with `Poz = 1` is the default-selected one.
 - `setari.php` (GET list + POST `update`) — edit `tblSet` (columns `Setting` PK, `Value`, `Descriere`, `Grup`); only `Value` is written. POST `{action:'update', values:{Setting:Value,...}}` saves a batch inside a transaction. `Grup` drives the tabs of the Setari screen.
 - `sync_products.php` (POST) — runs the stored procedure `dbo.ImportProd` (product/group/waiter/payment-form sync from the external source configured in `tblConectare` ID=1). It is **blocked while `tblNoteD` has any rows** (returns the message "Sincronizarea nu este posibila decat dupa efectuarea raportului Z al POS-ului."); sync is allowed only after the POS Z report. `GET ?check=1` only reports `{allowed, message}` without running anything, so the UI checks first and only asks for confirmation when allowed. `ImportProd` was adapted for the current Rual schema: reads `NrLogic` from the key/value `tblSet`, imports payment forms from source `tblTIB` into `tblFP`, writes `tblProd` with `PV`/`Nr_TVA`, skips the dropped `tblPV`, and always `ROLLBACK`s + `THROW`s on error. Triggered on demand by the **Sincronizare produse** button in the programming screen (`syncProducts()` in `js/pos.js`).

## Frontend
- All client logic is in `js/pos.js` (single global `POS_STATE`), wired to `index.html` via inline `onclick` handlers.
- Data loads: `initApp()` -> `loadMenu()` -> `loadOrder(1)` -> `loadTables()`. The app opens on the tables screen (`#screen-mese` has the initial `active` class in `index.html`), not on the marcare screen.
- Many bottom-bar buttons are placeholder toasts (e.g. Proforma) — verify before assuming an action persists to DB. (Mod Preparare, Transfer, Discount, VD, QTY, Marcare and Search are real flows.)
- The tables right menu has a **Coada printare** button (`openPrintQueue()`) that opens `#modal-print-queue` (state `printQueueRows`/`printQueueSelected`, data from `api/print_queue.php?action=list`), showing jobs (JobID, Tip, Ref, the destination printer `Kp`/`tblKP.NrLogic` with its name in the tooltip, Stare, Creat, Incercari); for `raport` jobs the Tip column shows the report name from the payload `title` via `printJobLabel()` (`Raport X - PLU/Grupe/Sectii/Casieri/General`, or just `Raport Z` for a Z job; `print_queue.php?action=list` returns it as `Title` using `JSON_VALUE(Payload,'$.title')`), with **Preview** (`#modal-print-preview`, an iframe on `api/print_preview.php?jobId=<JobID>` — a same-origin PHP proxy to the emulator, because the POS runs on HTTPS and a direct `http://127.0.0.1:8756` iframe would be blocked as mixed content), **Retry**, **Sterge** and **Goleste done** (Retry is enabled only for unfinished jobs — `pending`/`printing`/`failed`; a `done` job is not retried to avoid duplicates). `refreshPrintStatus()` (called from `loadTables` after Marcare/payment) adds a pending/failed counter to the button. `actionMarcare()` shows the server message (jobs enqueued); `finalizePaymentTransaction` shows the `print.nota`/`print.fiscal` job ids returned by `close_bill`.
- The reports screen (`#screen-rapoarte`) is opened from the login modal when the entered password matches `tblParola.ParolaRapoarte` (`authenticate` returns `rapoarte: true`, handled in `vkeyValidate()` -> `openReports()`). The **Rapoarte** button was removed from the tables right menu. It has two tabs (`REPORTS_TABS`: X, Z) rendered via `renderReportsTabs()`. The **X** tab shows the report buttons `REPORTS_TYPES` = PLU, Grupe, Sectii, Casieri, General (`renderReportsGrid()`), each calling `runReport('X', tip)`. **X - PLU is implemented**: `runReport` loads `api/rapoarte.php?tab=X&tip=PLU` and renders it in `#modal-raport` (`.raport-table`) grouped by section, with a subtotal per section and a grand total; **X - Grupe** and **X - Sectii** work the same via `tip=Grupe`/`tip=Sectii`, rendering a simple alphabetical list (`data.grupe`/`data.sectii`, value only); **X - Casieri** (`tip=Casieri`) renders one block per cashier (`data.casieri`) with Bonuri, Reducere, Stornari and the payment forms (`plati[]`), plus grand totals (`data.totalBonuri`/`totalReducere`/`totalStornari`/`totalPlati`/`totalValoare`); **X - General** (`tip=General`) renders the global totals (Bonuri, Discount, Stornari, TOTAL), the payment-form breakdown (`data.plati`), the VAT-by-rate breakdown (`data.tva`: Cota/Baza/TVA) and the notes list (`data.note`: NrNota/Masa/Ospatar/Total); the **Tipareste** button posts `{action:'print', tab, tip}` and enqueues a `raport` job (state `currentReport`). The other report types still show an "in curand" toast. The **Z** tab shows checkboxes `REPORTS_Z_OPTIONS` = PLU, Grupe, Sectii, Casieri plus the **Efectueaza Golirea Z** button (`actionGolireZ()`, asks for confirmation). `actionGolireZ` first calls `?tab=Z&check=1` (blocks with the server message if not all tables are closed), then `performGolireZ(tipuri)` posts `{action:'z', tipuri}`; the Z report always starts with General Z and appends the checked reports. On success it shows the Z number and refreshes the print-queue badge.
- When `tblSet.MeniulZilei = 1` **and** at least one product has `MZ = 1`, the marcare bottom bar shows a **Meniul Zilei** button (`#btn-meniul-zilei`, `actionMeniulZilei()`); it fills the blue panel slots left-to-right in alphabetical order with the `MZ = 1` products (ignoring their catalog `Poz`). Visibility is set by `updateMeniulZileiButton()` (called from `loadMenu`). The **Nota Proforma** button was moved from the marcare bar to the payment screen (`#screen-plata`).
- The marcare screen has a yellow scan box (`#scan-input`, `.scan-input`) in the note panel top-left (where the date/time used to be). It keeps focus while on `screen-marcare` and no modal is open (`focusScanInput()` on a 700ms interval, also called on entering the screen and after `addProduct`). On `Enter` it looks up the code by `BarCod` first, then falls back to `ProdID`, and calls `addProduct()` (products come from `menu.php`, which returns `BarCod`).
- All destructive/confirmation flows use the in-app confirmation `appConfirm(message, onYes, yesLabel, noLabel)` (`#modal-confirm`) instead of the native `confirm()`, which the POS browser may suppress (leaving buttons unresponsive): discarding unsaved changes in Setari / Mese / Grupe / Produse, the delete actions (produs, TVA, mesaj, ospatar, sectie, imprimanta, forma de plata) and product sync. `appConfirm` falls back to `window.confirm()` only if the modal is missing. Likewise all messages use `appAlert(message)` (`#modal-alert`) instead of the native `alert()` (also suppressed), with `window.alert()` as fallback.
- Payment screen (`#screen-plata`, opened by the `NOTA` button via `actionNota()`): the payment-method buttons (`#pay-methods-grid`) are rendered at runtime from `tblFP` (only `Status = 1`, ordered by `Poz`), loaded by `loadPaymentForms()` through `api/fp.php`; the form with `Poz = 1` is selected by default. Payment is split: pressing `OK` (`finalizePaymentTransaction`) records the numpad amount under the selected `FPID` in `POS_STATE.payments` (`{FPID: amount}`); if the total isn't covered it keeps the remaining and waits for another form, otherwise it calls `close_bill` with the whole `plati` array and shows the change. `updatePaymentProgress()` displays the recorded payments and the remaining amount in `#pay-progress`.
- The programming screen (`#screen-programare`, opened when the `tblParola.ParolaProgramare` password is entered) shows 12 option buttons (Setari, Grupe, Programare mese, Ospatari, Moduri preparare, Parole, Antet, Nota, Imprimante sectii, Forme de plata, Cote TVA, Conectare server). Only **Setari**, **Cote TVA**, **Moduri preparare**, **Ospatari**, **Imprimante sectii**, **Forme de plata**, **Programare mese**, **Grupe**, **Produse**, **Sectii**, **Antet**, **Nota**, **Conectare server**, **Parole** and **Sincronizare produse** are implemented. **Antet** navigates to the full-screen `#screen-prog-antet` (state `antetPlatitorTVA`) which edits only the `tblAntet` row with `Seria = '0001'`, via `api/antet.php`: fields Nume, Denumire2, Adresa, Oras, CodPostal, CodFiscF, RegCom, Judet, Cont, Banca, PersContact, email, website, telefon, PlatitorTVA (Da/Nu toggle), CaleDateLogo, QRCodeText and SizeModeLogo. **Nota** navigates to the full-screen `#screen-prog-nota` which edits the `tblAntet` header/footer rows `H1`,`H2`,`H3`,`F1`,`F2` via `api/nota.php` (state `notaRows`), rendering one card per row with Nume, an ESC/POS NumeFont combobox (`NOTA_FONTS`: Font A/B/C/D/E), a Size magnitude combobox (`NOTA_SIZES`: 1x1/2x1/1x2/2x2/3x3) and a Bold Da/Nu toggle; saved in a batch. **Conectare server** navigates to the full-screen `#screen-prog-conectare` which edits the single `tblConectare` row (`ID = 1`) via `api/conectare.php`: fields ServerIP, ServerName, DataBaseName, UserName, Password, TC (combobox Da/Nu, `bit`) and ODBC_connect_string, plus a **Testeaza conexiunea** button (`testConectare`) that tests the on-screen values. **Parole** navigates to the full-screen `#screen-prog-parole` which edits the single `tblParola` row (`Id = 1`) via `api/parole.php`: numeric passwords for Programare, Rapoarte, Stornare, Discount and Exit (empty = not required), each with a numeric keypad. **Setari** navigates to the full-screen `#screen-prog-setari` with four tabs (General / Device-uri / Imprimante / Altele) driven by `tblSet.Grup`: General shows `Grup='General'`, Device-uri shows Casa/Cantar/Afiseaj, Imprimante shows Nota/KP, Altele shows everything else; only `Value` is editable (saved in batch via `api/setari.php`), state `setariRows`/`setariDirty`/`setariActiveTab`. The first five open editors for `tblTVA` / `tblMesaj` / `tblOsp` / `tblKP` / `tblFP`. **Programare mese** navigates to a dedicated full-screen editor `#screen-prog-mese` (not a modal) with a live 10x8 map (`#mese-prog-grid`) and a right inspector (`#mese-inspector`) that writes to `tblMese` via `api/mese.php`. Its state lives in `meseWorking`/`meseDirty`/`meseSelected`; changes update the map instantly and persist only on Salveaza. **Grupe** navigates to the full-screen editor `#screen-prog-grupe` with a live 5x10 grid (`#grupe-prog-grid`) mirroring the menu grid on `Poz 1..50` and a right inspector (`#grup-form`), state `grupWorking`/`grupDirty`/`grupSelected`, writing to `tblGrp` via `api/grupe.php`; no delete. **Produse** navigates to the full-screen editor `#screen-prog-produse` with a **Grupa** `<select>` on top and a live 5x10 grid (`#produse-prog-grid`) of that group's products (`Poz 1..50`); state `prodWorking`/`prodDirty`/`prodSelected`/`prodCurGrup`, writing to `tblProd` via `api/produse.php`. Its inspector edits all `tblProd` columns except `DataUM` (always `GETDATE()`), exposing **Sectie** and **Nr_TVA** as `<select>`s populated from `tblSectii` / `tblTVA`, plus delete (with confirm). The remaining buttons just fire a `progAction()` toast and are stubs awaiting implementation. Its header has a "⌨️ Tastatura" toggle that shows a floating QWERTY overlay (`#modal-fkb`) which writes into whatever text box currently has focus (used when no physical keyboard). The overlay carries punctuation on the Shift layer (`[ ] \ ; ' , . / -` with `{ } | : " < > ? _`), so no extra symbols row is needed. When opened via a field's `⌨️` button (`openFloatingKeyboardFor`), the overlay is auto-positioned (`positionFloatingKeyboard`) above or below the target field — and `fkbEnsureFieldVisible` scrolls the field's container if needed — so it never covers the field being edited; it can still be dragged by its header (drag coordinates are converted through the stage scale). In the programming editors, **numeric** fields (ProdID, KP, PV, Poz, FontSize, IRP, IIVCN, NrGrp, NrMesaj, Sectie, FPID, NrOsp, FP Poz, and the KP editor's NrLogic/MagID/raport) use a numeric keypad (`openNumericKeyboardFor()` -> `#modal-num`, button labelled `123`), while **text** fields keep the QWERTY floating keyboard (`openFloatingKeyboardFor()`, button `⌨️`).
- **Canvas scaling (both axes free, min 1024x768)**: base design is 1024x768 in `#pos-stage`. An inline script in `index.html` `<head>` sets on `<html>`: `--pos-scale = min(w/1024, h/768)`, `--pos-stage-w = max(1024, w/s)`, `--pos-stage-h = max(768, h/s)`. The stage's *unscaled* size grows past 1024x768 on axes where the screen is more generous, so the scaled canvas covers the window exactly (no green bands). Surplus space flows into flexible regions: extra width -> right/blue panels (menu grid); extra height -> grid rows, note item list, tables grid. Fixed-px parts (410px note panel, arrow column, top/bottom bars) keep their px but grow with the scale factor. NOT vw/vh responsive CSS. The menu grid always renders 50 cells (empty ones get `.empty`) -> exactly 10 rows of 5.
